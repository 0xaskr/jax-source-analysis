# 【Research Plan】: JAX 软件栈索引 Kickoff（Draft）

## 1. 背景与动机

    在 模型与 kernel 优化工作中，经常需要理解/修改，软件栈其他层级代码来解决问题。面对这些问题，仅单一层级源码难以判断问题出在哪里，如果修改，应该在哪里修改、修改会受到哪些约束，以及如何验证结果。

    未来我们还会遇到类似的问题，而且这些问题涉及整个软件栈，围绕单个问题的零散排查很难形成整体认识。因此，我们需要系统性建立一份从 JAX 到硬件的软件栈索引，梳理各层的作用、相互关系和对应的源码位置，为后续理解问题、定位修改位置和选择验证方式提供依据。

    即使 AI 辅助理解和修改代码，我们仍然需要这份索引：开发者需要知道 AI 应该修改哪些部分、往什么方向修改才是正确的，以及如何验证结果（如果连 AI 的修改都无法理解和验证，那不过是在向 AI 许愿）。AI 可以帮助我们学习软件栈、整理索引和开展实验，但开发者仍需形成自己的理解，并验证 AI 产出的正确性。

下面给出 5 个需要跨层级来解决问题的case。

| 案例与来源 | 成员遇到的问题 | 需要跨层理解的内容 |
|-------|---------|-----------|
| HLO 图编辑接口不足（`Iamleos`，[JAX #39023](https://github.com/jax-ml/jax/issues/39023)） | 已能注册 HLO 变换回调、反序列化计算图，但希望增加指令、复制或编辑图时，现有 Python 接口不足 | HLO 表示、Python 与原生代码之间的绑定，以及编辑接口的实现和构建位置 |
| 编译回调挂起（`hhhhsdxxxx`，[JAX #38829](https://github.com/jax-ml/jax/issues/38829)） | TPU 提前编译（AOT）过程中，Python 变换回调尚未进入便发生挂起；报告沿编译线程和锁的等待关系排查 | 从 JAX 编译入口到 jaxlib、PJRT/IFRT 的调用链，以及 Python 全局解释器锁（GIL）与编译线程的交互 |
| 训练通信需要调整设备映射（`wangfakang`，[JAX PR #39340](https://github.com/jax-ml/jax/pull/39340)） | TPU v7 训练中的通信映射需求推动了 JAX mesh 构造规则的修改，将物理轴的带宽差异纳入候选选择 | 逻辑设备网格、物理拓扑、通信需求，以及 JAX 中负责映射的源码规则 |
| Pallas kernel 遇到编译限制（`pathfinder-pf`，[JAX #39577](https://github.com/jax-ml/jax/issues/39577)） | BF16 gather 在特定 SparseCore 间接传输操作处报出仅支持 32 位元素的错误 | 从 Pallas 表达到底层传输操作的编译过程，以及数据类型、编译支持与硬件能力的边界 |
| 性能分析中缺少 LLO 信息（`Prayer3th`，[XProf #2441](https://github.com/openxla/xprof/issues/2441)） | 对训练过程采集性能数据后，在 XProf 中看到大量 LLO 区域为空；讨论涉及 libtpu 版本和界面显示范围 | LLO 调试信息、运行时采集与性能分析界面之间的关系，以及如何确认观测信息是否完整 |

## 2. 目标

从 JAX 源码出发，**系统梳理理解 JAX 软件栈及其组件**， **建立索引**，记录各组件的职责、相互调用关系和关键衔接处的 API。 结合具体问题，通过阅读索引和源码，**实现简单的 Hack**，按需编译并实际验证， 加深对相关机制的理解，为后续问题定位、代码修改及 AI 产出验证提供依据。

具体目标如下：


1. **梳理软件栈**: 梳理JAX/jaxlib、StableHLO、Shardy、XLA（含 IFRT/PJRT）、 LLVM/MLIR、Pallas/Mosaic、libtpu 等组件及其与 CPU/TPU 硬件的衔接关系。 列出主要组件、职责和依赖关系及其关键API。标出CPU/TPU 后端分支， 分别说明普通 JAX/XLA 与 Pallas/Mosaic 的编译路径, 展示程序从 JAX 入口经过编译、运行时到硬件执行的主要衔接点.
2. **《源码与 API 索引》**：以matmul为例，组合使用`jit`、`grad`、`vmap`等API， 按组件进行索引，记录对应的源码目录、关键函数或类、上下游调用关系， 以及衔接处 API 的输入输出和使用约束。
3. **完成简单的 Hack 并验证**：以实际需求为例，从简单的修改入手，例如增加 编译过程的诊断信息、对一个小型计算图做局部改写。通过索引找到相关代码，阅读源码 确认修改方式，完成修改并按需编译、安装，运行最小示例验证变化是否符合预期。 围绕每个 Hack 保留相关源码说明、修改补丁、构建和验证脚本、修改前后的中间产物 （IR）、日志或数值结果，以及回滚方法，形成可复现的实验案例。源码导读、环境 准备和构建说明随具体 Hack 一起整理。

具体研究目标按对象展开如下：

| 研究对象 | 具体研究目标 |
|------|--------|
| 组件关系 | 梳理 JAX/jaxlib、StableHLO、Shardy、XLA、LLVM/MLIR、Pallas/Mosaic、libtpu 的职责、依赖与关键接口，明确 CPU/TPU 后端分支及组件之间的衔接位置 |
| matmul 的 lowering 全过程 | 以 matmul 为例，从 JAX 表达经 tracing 形成 Jaxpr，追踪其 lowering 为 StableHLO/HLO 并进入后端代码生成的完整过程；梳理各阶段的程序表示、转换规则、关键接口与对应源码，并关联实际取得的 IR 和编译产物 |
| 编译、缓存与执行 | 追踪 `jit` 从 JAX 进入 jaxlib、XLA 和 IFRT/PJRT 的关键调用，解释编译请求、可执行程序与执行请求的衔接；用实际运行记录区分首次调用、缓存复用和输入规格变化时的行为 |
| TPU 与 Pallas/Mosaic 路径 | 分别建立普通 JAX/XLA TPU 路径和 Pallas/Mosaic kernel 路径的索引，解释内层 kernel 与外层调用的关系；按取得的源码和产物补充 libtpu、LLO 与硬件对应关系，涉及分片时补充 Shardy 等相关路径 |
| 简单 Hack | 围绕编译诊断信息、小型计算图局部改写等需求，通过索引找到修改位置，确认接口约束，完成修改、按需编译和验证，说明预期变化、实际效果与回滚方法 |

## 3. 交付产物

交付分为三组，分别对应软件栈梳理、源码索引和简单 Hack：

| 产物  | 格式  | 具体内容 |
|-----|-----|------|
| 软件栈总览 | Markdown 文档、Mermaid 图 | 组件职责与依赖清单、CPU/TPU 后端分支、关键 API 列表，以及普通 JAX/XLA、Pallas/Mosaic 和运行时调用的架构图与流程图 |
| matmul 源码与 API 索引 | Markdown 导读、JSON 索引、Python 示例、IR 与日志文件 | 按组件组织的源码入口、关键函数或类、上下游调用关系、API 输入输出与约束；matmul 及 `jit`、`grad`、`vmap` 组合示例，以及与源码条目对应的实际采集样本 |
| 简单 Hack 实验集 | Markdown 说明、patch 文件、Python／Shell 脚本、JSON 实验记录与结果文件 | 每个 Hack 的问题与修改理由、相关源码说明、可逆补丁、环境准备与按需构建步骤、加载检查、运行与验证脚本、修改前后对照及回滚记录 |

文档、索引和实验记录相互关联，标明源码版本、验证依据、适用范围及待补齐内容。 源码导读、环境准备、构建与调试说明随具体 Hack 一起整理，实验中确认的接口约束 和验证方法补回总览与索引。

## 4. 研究方案

以 matmul 示例串联源码阅读和索引建设，再用简单 Hack 检验索引是否足以支持 实际修改。复用已有源码清单、架构资料和实验工具，逐步补充具体调用与运行证据。

### 4.1 确定源码、研究边界和实验条件

从 JAX 的计算入口向下研究，重点覆盖 CPU/TPU 路径。模型或 kernel 框架提供具体 问题与最小输入；分析从其调用 JAX/Pallas 的位置开始。采用以下固定源码版本：

| 组件  | Git revision |
|-----|--------------|
| JAX | `5832e866449a41c3eea6333416528039119a0fde` |
| XLA | `496bd4bd49db9ecbffd85da630b49c860b724604` |
| StableHLO | `7b1b15781ccbd770f50c7eef4b0c3e03834649fd` |
| Shardy | `eb23a98329aa70d991aa2d8a51a209af1f8df8fc` |
| LLVM | `ab547095ead5464dc024d66264d9b8a987f429f3` |

实验同时记录 Python、构建工具、实际加载的二进制及其版本和指纹。源码阅读和 架构索引可以先开展；涉及编译、执行或原生组件修改时，补齐对应环境并检查来源。 TPU 内部实现与硬件行为的研究需要相应 libtpu 源码或编译产物、目标配置及设备条件， 未取得的资料列入待补齐清单。

### 4.2 建立 matmul 最小示例

固定输入形状、数据类型、随机种子与数值参考，依次构造以下示例：

* **基础 matmul**：两个矩阵相乘，作为源码追踪和数值对照的起点。
* **批量计算**：用 `vmap` 对一组输入矩阵应用同一个 matmul，跟踪批量维度与程序表示的变化。
* **求导**：将计算结果的平方和归约为标量损失，对输入或参数使用 `grad`，观察求导后的程序。
* **组合与编译**：用 `jit` 包装上述计算及求导，记录首次调用、相同输入规格的再次调用， 以及输入规格变化时实际发生的 tracing、编译与执行。

先在 CPU 上建立可运行对照，保存示例代码、断言、实际取得的程序中间表示（IR）和 日志。每个样本写清楚对应哪一个示例、哪个阶段及哪次运行。

### 4.3 沿示例建立组件与 API 索引

从 matmul 的 JAX 入口出发，结合固定源码与实际产物，逐步定位程序变换、Jaxpr、 StableHLO/HLO、编译调用、可执行程序与执行请求之间的衔接。 将 host 上的调用关系与编译器内部的程序变换关系分别记录。

每个索引条目包含：组件、源码 revision、文件路径、关键函数或类、调用方与被调用方、 API 输入输出和使用约束、关联示例、验证依据及待确认问题。Markdown 用于阅读说明， JSON 用于保存结构化条目和相互引用。

CPU 与 TPU 的共同部分共用索引，后端差异分别记录。普通 JAX/XLA TPU 路径与 Pallas/Mosaic TPU 路径分别追踪；后者保留内层 kernel 表示与外层调用的对应关系。 Mosaic TPU MLIR 不称为 LLO。取得匹配资料后，再继续补充 libtpu、TPU-specific LLO 与硬件执行的索引条目。

### 4.4 从简单 Hack 验证修改能力

根据实际需求选择修改位置，先写明预期变化、需要保持的行为及验证方法。优先尝试 以下两类小实验，具体函数与接口由前面的源码追踪确定：

| Hack 方向 | 修改内容 | 验证方式 |
|---------|------|------|
| 编译诊断信息  | 在已定位的编译入口或阶段增加诊断信息，例如输入形状、阶段名称或回调是否进入 | 检查日志出现的位置和条件是否符合预期，并比较修改前后的数值结果 |
| 小型计算图的局部改写 | 对 matmul 示例的局部计算做明确的变换，例如在输出后加入固定缩放，并写出对应参考计算 | 对比修改前后的 IR，检查运行结果是否符合变换后的参考；涉及求导时同时检查对应梯度 |

通过索引找到代码后，阅读上下游约束、实现修改、按需编译和安装，确认运行使用了 预期修改产物，再执行对照与必要的边界检查。每次实验保留补丁、构建和运行命令、 原始结果及回滚步骤，并将新的认识补回索引。

### 4.5 验证与资料整理

源码导读中的结论对应固定版本的源码入口，运行结论对应实际采集的产物。实验记录 包含输入、命令、环境、二进制身份、产物指纹、预期与实际结果。按实际工作标记证据：

| 标记  | 表示完成的工作 |
|-----|---------|
| `SOURCE-ONLY` | 检查固定版本的源码、接口或构建定义 |
| `RUN-CPU` | 在真实 CPU 后端运行并检查结果 |
| `SIM-TPU` | 用 TPU/Pallas interpreter 进行模拟验证 |
| `COMPILE-TPU` | 针对记录的 TPU 目标完成编译 |
| `RUN-TPU` | 在记录的真实 TPU 设备上运行并检查结果 |
| `REPLAY-OFFLINE` | 重放或分析已有且可追溯的采集产物 |

运行二进制与引用源码不一致时增加 `VERSION-SKEW`。CPU 结果不能外推为 TPU 的 运行、LLO、硬件、通信、内存或性能结论；TPU 模拟、编译与真机执行分别取证。

AI 可以辅助检索、解释和修改；开发者沿索引核对源码依据、审阅修改并复查验证结果。 文档与实验记录一起维护，大体积或私有材料保留在 Git 外，记录脱敏位置和指纹。
